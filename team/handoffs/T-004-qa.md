**start_age semantics**
- Tyre ages run `start_age .. start_age+laps-1`. I checked this by oracle: the lap-to-lap increments of a `start_age=6`, 5-lap HARD stint equal laps 6..10 of a fresh 10-lap stint.
- Pit loss is keyed on `lap_in_stint == 0 and stint_index > 0`. A 3-stint strategy with used sets 2 and 3 gets `pit_laps == [6, 11]` and exactly 2 x pit_loss. A used first stint gets no pit.
- `start_age < 1` is rejected in both places.
  - The dataclass raises ValueError for 0, -1 and -100.
  - The API returns 422 for 0, -1, 1.5 and explicit `null`.
- Omitting `start_age` gives a response byte-identical to `start_age: 1`, checked through the API with seed 1.
- Very large start_age (500) stays finite and slower than a new set.

## Assessment of the near-deterministic win_probability claim
The claim is correct, and it is not a bug.
- Under CRN with purely additive iid noise, any two strategies with the same race length and stop count share every draw. Their difference is the constant deterministic gap, and the win outcome is 0 or 1 in every iteration. I reproduced it with the author's strategies. 1-stop M25/H32 gets 0%, 2-stop S15/M20/H22 gets 2.3% and 1-stop H30/M27 gets 97.7%. The 2-stop strategy gets only that 2.3% through its extra pit draw.
- The implementation is consistent with this. The fix for the old behaviour (43% / 46%) was exactly the point of ROADMAP item 3. The old figures were the artefact, because independent noise on a 0.3s edge produced coin-flip shares.
- The caveat is semantic, not mechanical (N-1). A 0.31s mean edge is reported as 98%, and replay errors against real races are 26 to 150s. So `win_probability` is now effectively `argmin(mean)` with no uncertainty content for like-for-like strategies. Nothing in the API response conveys that.

## Findings

**N-1 (medium, semantics/UX) — `win_probability` over-communicates certainty.**
- Where: the response field `win_probability` in `simulation.py`, and the frontend copy.
- Repro: compare two 1-stop strategies of the same length within ~0.3s; the result is 0% / 98%.
- Owner: orchestrator decides. Backend-engineer should add the paired delta (mean and p10/p90 of strategy minus best) to the response. Frontend-engineer should avoid presenting the percentage as confidence, and should show "tie" / "no meaningful difference" for deltas below the model error. Also consider splitting wins evenly for exact or near-exact ties. Today the first-listed identical strategy gets 100%, which is arbitrary.

**N-2 (low-medium, pre-existing but amplified) — unequal total laps are accepted.**
- Where: the API does not check that strategies have equal total laps.
- Repro: a 40-lap and a 30-lap strategy return means 3668.7 vs 2747.0 and win_probability 0.0 vs 1.0. Under CRN the shorter race always "wins".
- Owner: backend-engineer. Validate equal totals, or at least return a warning. The frontend should also validate.

**N-3 (medium for model quality, not a T-004 bug) — fitted SOFT curve is flat for 37 laps.**
- Where: `tire_model.predict_delta` with the real fitted model, which gives SOFT delta = 0.00 for ages 2..37 and +0.05 at age 1.
- Effect: a used SOFT set (start_age 5) simulates *faster* than a new one (897.42 vs 897.47). MEDIUM and HARD give the physically sensible ordering. So `start_age` is effectively a no-op for SOFT until it hits the flat placeholder cliff. 20 laps of SOFT is also free.
- Owner: data-scientist (the T-002 refit). This sits alongside the existing placeholder warnings. The author's own request to check how often used-set ages exceed `max_reliable_age` still applies.
- Note: my API test therefore uses HARD, not SOFT.

**N-4 (low, docs) — caveats live in one docstring.**
- The "additive noise only" caveat and the "win_probability is now near-deterministic" consequence are documented in `simulate_totals` only. Add one line to the module docstring (SCOPE NOTE) and to the `compare_strategies` docstring, and ideally to the `win_probability` field description in `StrategyResult`.
- Owner: backend-engineer.

**N-5 (low) — memory is now O(n_simulations x laps) and `laps` has no upper bound.**
- Where: `monte_carlo.py:139-143` (lap_noise, plus cumsum and hstack copies); `StintIn.laps` is `Field(gt=0)` only.
- Repro: 50k sims x 78 laps peaks at 94 MB (fine). A 2000-lap stint at 50k sims ran in 2.6s on this machine but allocates about 0.8GB per matrix. A large enough `laps` would raise MemoryError (500) rather than just run slowly. The old loop was only CPU-bound.
- Owner: backend-engineer. Cap `laps` (e.g. `le=100`) and/or total laps in the API.
