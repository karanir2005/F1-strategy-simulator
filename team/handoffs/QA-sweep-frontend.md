# QA sweep: frontend (pre US GP weekend), frontend-engineer, 2026-10-23

Review only, no code changed. `npx tsc --noEmit` is clean and `npm run lint` is clean. I checked the live :3000 and :8001 responses. I also drove headless Edge over CDP against the dev server: /predict and /strategy at 360px (no horizontal overflow on either), /predict with the backend blocked (ErrorBlock and retry render correctly), and /predict with a mocked grid-mode response (badge, grid note and "What changed" render). Not exercised: optimize or simulate result rendering in a browser, and light mode.

## Findings (most severe first)

1. **HIGH: the countdown and the status line disagree, and the countdown targets the wrong time.** Files: `components/predict/countdown.tsx:84-91`, `race-header.tsx:14-22`. The countdown counts to 00:00 UTC of the session date, but the status line uses the viewer's local calendar date. At 22:34 EDT today the page showed "Qualifying in 1 day. Lights out in 2 days." directly above "RACE DAY STARTS IN (UTC MIDNIGHT) 00d 21h". It skipped qualifying because 24 Oct 00:00Z had already passed. For a US viewer it reaches zero at about 19:00 CDT on Saturday and then disappears on race eve. The actual COTA race start is roughly 43h away, not 21h. Fix: the backend should add `race_start_utc` / `quali_start_utc` (Jolpica has session times). Until then, drop the h/m/s and count whole days with the same local-date logic as the status line.
2. **MED: strategy results go stale after settings change, and the optimizer has a race condition.** File: `app/strategy/page.tsx:122-129, 136-163`. `selectTrack` clears `optResult` but not `results`, so the manual comparison stays on screen under the new track. `CompareResults` never names the track or the safety-car setting it was run with. An optimize request still in flight when the user switches track writes the old track's plan onto the new one. Fix: keep a request token or AbortController, clear `results` on track change, and label results with their track and SC setting.
3. **MED: safety-car copy is wrong when SC is on, and `assumptions` from /simulate are ignored.** File: `components/strategy/compare-results.tsx:21, 137-139`. The text hard-codes "no safety cars or traffic yet". `SimulateResponse.safety_cars` and `assumptions` are typed in api.ts but never rendered. OptimizerResults does render its assumptions.
4. **MED: manual plans are not checked against the track's race distance.** File: `lib/strategy-form.ts:441-453`. Validation only requires the plans to have equal totals with each other. Plans edited to 50 laps at Austin (56) run a 50-lap race with no error, and the only warning is a sentence in race-settings.tsx:179. Add a soft warning or validation error when a plan's total differs from `track.total_laps` and the user is not overriding.
5. **MED (mobile): no numeric gap-to-best below 640px.** File: `components/viz/range-plot.tsx:157-160`. The `right` column is `hidden sm:block` and the plot is aria-hidden. On phones the optimizer's "+x.x s vs best" values are not shown anywhere as text. "Top plans" shows only absolute times. Screen readers also get only the labels.
6. **MED (copy): the two strategy panels state different noise floors.** The manual results say "about a second or less" is noise (`compare-results.tsx:132`). The optimizer uses `NOISE_FLOOR_S = 5` s ("within noise" badge). Use one number on both.
7. **LOW: key context is only in `title` tooltips**, which touch and keyboard users can't reach. The US GP track notes ("all data is from the 2025 race… may differ from 2026 pace") sit only in the badge `title` (`race-settings.tsx:107`). The same applies to DELTA_HELP / WIN_PROB_HELP headers and the track-wear reason.
8. **LOW: the optimizer copy is wrong when only one plan comes back.** File: `optimizer-results.tsx:142`. It renders "The next plan is +0.0s behind… outside the 5 s noise band".
9. **LOW: the headline makes an unconditional claim.** File: `hero.tsx:229`. "A favourite at this level still loses most of the time" is false whenever p_win > 0.5. Gate the sentence on p_win < 0.5.
10. **LOW: in grid mode, the Qualifying tab shows the saved pre-quali pole odds after qualifying has happened**, and only the footnote explains that (`probability-table.tsx:302-308`). Label the column header "Predicted before qualifying".
11. **LOW: on the stale fallback with an unknown date** (`prediction_service.latest_saved`, date `""`), `weekendStatus` reports "race finished" because NaN falls through to that branch. `fmtDay("")` also renders "Round 18 · ". Guard against NaN.
12. **LOW: robustness and contract notes.** Contract drift is otherwise nil: all response fields match the pydantic models.
    - `/predict/next` uses `response_model_exclude_unset=True`. The code checks `grid === null` and `actual_grid !== null` (`probability-table.tsx:44,108,125`). Today the service always sets those keys, but if one is ever omitted the UI shows "Pundefined". Use `== null`.
    - `fetch` has no timeout, so if the backend hangs the predict skeleton or "Searching..." spinner never ends.
    - Backend CORS allows only `http://localhost:3000`, and `.env.local` points at `127.0.0.1:8001`. Opening the app via 127.0.0.1:3000 or a LAN IP (e.g. phone testing) shows "cannot reach the backend", which is misleading.
    - The "Is the backend running?" hint also appears on 422 validation errors (`strategy/page.tsx:305`).
    - The radiogroups (`probability-table.tsx:174,191`, `manual-compare.tsx:291`) have no arrow-key handling.

## Small UX improvements worth doing
- Show session times in the viewer's local timezone with the countdown ("Race: Sun 14:00 CDT"), once the backend provides start times (fixes #1 properly).
- On /strategy, add a one-line results caption: "Austin · 56 laps · SC off · run 22:41", plus a "results are out of date, re-run" chip when settings change after a run (covers #2 and #3).
- Show Austin's 2025-data note inline under the badge, not in a tooltip, and rename "Simulations per strategy" to "Simulations (manual compare)". The optimizer always uses the backend default of 2000 and ignores this field.
